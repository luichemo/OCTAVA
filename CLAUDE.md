This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Product

OCTAVA is a Tinder-style app for forming bands. Musicians swipe on each other, and bands post open roles that musicians swipe on. The owner is building it alone.

Decisions the owner has made (build to these; don't ask about them again):
- **Audience:** all kinds of musicians: beginners and hobbyists, working musicians, existing bands looking for members, and session or one-off players.
- **Platforms:** iOS and Android, mobile first. The web version is only a preview for testers, published to GitHub Pages at https://luichemo.github.io/OCTAVA/ by `.github/workflows/pages.yml` on every push to `main` (it runs analyze and the tests first). It uses the real Supabase project, so testers create real accounts.
- **Reach:** worldwide from launch. The UI is in English and Georgian (done; see Code layout → Translations).
- **Ages:** 16+. People aged 16–17 can join bands with adults but cannot have one-on-one private chats with adults. Enforce this on the server, not only in the UI.
- **Matching:** a match happens when two people both swipe right.
- **Bands (decided 2026-10-13):** any user can create their own band (and be in several). A member can propose someone they've matched with; **every** other member must approve (one no cancels it), then the person gets a join request and accepts or declines. No chat is needed for a request; it appears in their Bands section. Teens and adults never match, so mixed bands form through **band cards in the feed**: bands appear as cards that teens (and adults) can swipe Jam on, which is a join request that every member must approve. Safety rule (owner, 2026-10-13): a teen can join a band with adults only if it already has at least 2 members (and an adult can join a teen band only at 2+), so a mixed band always has 3+ people and its chat is never a private teen–adult chat in disguise. If members leave and a mixed band drops to one teen and one adult, its chat locks until someone else joins. Enforce this in the database. Removing a member (2026-10-16) takes a majority of the other members (3 members → 2 agree); the person being removed doesn't vote or see the vote.
- **Profiles:** instruments (several, each with a skill level), genres and influences, gear and logistics (own kit, car, rehearsal space, home studio), availability and goals (fun, gigging, recording, paid). Samples are uploaded audio clips plus links to YouTube, TikTok and other social media. Video upload is not planned.
- **Swipe filters:** distance, instrument or role, genre and skill level, goals and availability.
- **Chat:** one-on-one text, band group chat, voice messages and audio.
- **Band tools:** public band page, rehearsal calendar, songs and setlists.
- **Money:** free for now; no payments, subscriptions or ads.

## Release plan

Keep version 1 small, because one person is building it.
1. **Version 1:** sign-up with date of birth (16+), profiles with audio clips and links, swiping with the filters above, matching on mutual likes, one-on-one chat with the teen restriction, report and block, English and Georgian.
2. **Version 2:** bands (create, propose a match, unanimous approval, accept), band group chat, then band cards in the feed (how teens join bands with adults), voice messages.
3. **Version 3:** public band page, rehearsal calendar, songs and setlists.

Stack (chosen by the owner): **Flutter** (Dart) for the iOS and Android app, and **Supabase** for logins, the Postgres database, audio storage and real-time chat. The owner knows JavaScript/TypeScript but is new to Dart, so briefly explain Dart-specific patterns when introducing them.

## Code layout

Sign-up, profile setup and swiping use Supabase. Screen state lives in each screen (`setState`). No state-management package has been chosen yet.
- `lib/main.dart`: initialises Supabase, then runs `OctavaApp` (MaterialApp with light and dark themes). `OctavaApp(home:)` defaults to `AuthGate`; tests pass their own home so they don't need Supabase.
- `lib/config/supabase_config.dart`: project URL and publishable key. These are public by design; never add the secret/service_role key or the DB password.
- `lib/screens/auth_gate.dart`: `AuthGate` listens to Supabase auth. Signed out → `AuthScreen`; signed in → `ProfileGate`, which asks the repository for a `ProfileStatus` (needsBirthDate / needsProfile / ready) and shows `OnboardingScreen` or `SwipeScreen`.
- `lib/screens/matches_screen.dart` and `lib/screens/chat_screen.dart`: opened from the swipe screen's Matches button, or from "Say hi" after a match (`SwipeScreen.onOpenChat`; `DeckSource.swipe` returns the match id). `lib/data/chat_repository.dart` loads matches with each person's main instrument and latest message, streams a match's messages live (`.stream()` = Supabase Realtime, RLS applies), and maps RLS refusals (42501: blocked or age rule) to a message. `ProfileGate(chat:)` is optional; without it there's no Matches button.
- Live updates: `lib/data/live_updates.dart` (`LiveUpdates`, a ChangeNotifier owned by `ProfileGate` for the whole session) loads matches and listens to `ChatRepository.changes()`, one Realtime channel for inserts on `messages` and `matches`, deletes on `matches`, and any change to `match_reads`. On each change it reloads the matches; overlapping reloads merge into one. It provides the Matches list (`MatchesScreen(live:)`; without it the screen makes its own), `unreadTotal` for the badge on the bottom bar's Matches button, `theirLastReadAt` for "Seen" under your newest message, `matchSetVersion` (the swipe screen reloads the band row when it changes), and `banners`. `LiveBannerListener` (`lib/widgets/live_banner.dart`, around the swipe screen) shows banners in the navigator's root overlay, so they appear over any page, for 4 s. Tapping a banner opens that chat; swiping it up dismisses it. Banners appear for messages outside the open chat and for matches someone else completed (`matches.created_by`; your own swipe already shows the dialog). `ChatScreen(live:)` calls `openChat`/`closeChat`, which mark the chat read (`ChatRepository.markRead` upserts `match_reads`). `openChat` runs from initState, so it notifies listeners in a microtask, after the build.
- Bands (v2): `lib/data/bands_repository.dart` (`BandsRepository`; `SupabaseBandsRepository` loads bands, members, open proposals and votes in one go and calls the band database functions; `bandErrorMessage` turns the functions' English rule errors into translated `errBand*` messages, matched by key phrases, so keep them in step if a migration rewords one). Models in `lib/models/band_group.dart` (`MyBand`, `BandPerson`, `BandProposal`, `BandInvite`, `BandsState`); not to be confused with `lib/models/band.dart`, the personal lineup row. `LiveBands` (`lib/data/live_bands.dart`, owned by `ProfileGate` when both `bands` and `chat` are given) reloads on any Realtime change to the band tables; its `actionCount` (invites + votes waiting for you) is added to the Matches badge. `MatchesScreen(bands:)` shows a Bands section above the matches: Create a band (a name dialog, then the new band opens), invite cards (Accept / Decline) and one tile per band (member count, or "N votes waiting for you"). `BandScreen` (`lib/screens/band_screen.dart`): members ("You" marked), Add member (a sheet of your matches not in the band or already proposed), New members (each proposal with who proposed, "N of M approved" or "Invited", and Approve / Reject, Reject asks first; on your own requests, or ones left by someone who left, **Cancel request**, which asks first) and ⋮ → Leave band (asks first, then goes back). Each other member's row has a ⋮ with **Remove from band** (a confirm, then `proposeRemoval`); open removal votes show under "Removing members" (`_RemovalCard`: who proposed, "N of M needed", Remove / Keep, Cancel vote for the proposer). `MyBand.removals` (`BandRemoval`, with `neededIn(memberCount)`) count toward `votesWaitingFor`. Band chat (`lib/screens/band_chat_screen.dart`, `BandChatScreen`): tapping a band in Matches (or a band banner, or creating one) opens its chat; the app bar's group icon (badged with votes waiting) opens `BandScreen`. It reuses `ChatBubble` / `DayChip` / `sameDay` from `chat_screen.dart` (`ChatBubble(sender:)` puts the name above the text); other people's runs of messages end with a small avatar (no names; tapping the avatar opens a bottom sheet with their picture, name and role, `_showPerson`), bubbles hug their text (`IntrinsicWidth` in `ChatBubble`), and your newest message shows "Seen by N" / "Seen by everyone" from `MyBand.readMarks`. While `MyBand.chatOpen` is false the input is replaced by a yellow notice: alone, "Add a member…"; otherwise the teen/adult 3+ rule. `BandsRepository` also streams `messages`, `send`s (42501 → `errBandSendClosed`) and `markRead`s (`band_reads`); `load` adds `chatOpen` (from the `my_band_chats()` RPC), `unreadCount` (from the latest 500 band messages), `lastMessage` and `readMarks`. `changes()` emits `BandMessageArrived` / `BandsChanged`. `LiveBands` has `openChat`/`closeChat` (like LiveUpdates), `unreadTotal`, `badgeCount` (actions + unread, on the Matches button) and `banners`; `LiveBannerListener(bands:, onOpenBand:)` shows them like match banners. Band profile (step 5b): the top of `BandScreen` is `_BandProfileCard` (description, "Looking for: …" from `openRoles`, genre chips, and the band clip with play / record-or-upload / remove). **Edit** opens `BandProfileScreen` (`lib/screens/band_profile_screen.dart`: name, description ≤ 500, `GenrePicker` ≤ 10, open-role `FilterChip`s ≤ 8; saves with `BandsRepository.updateProfile`). ## Backend (Supabase)

Project ref `nbvcbhnaevkrnpbjhbbj` (Frankfurt). Claude Code reaches it through the Supabase MCP server in `.mcp.json`; the owner authenticates with `/mcp`. The schema lives in `supabase/migrations/`, with file names matching the versions applied remotely. Add changes as new migration files (apply with the MCP `apply_migration` tool, then save the same SQL locally under the version it gets). Don't edit applied migrations.

How v1 fits together:
- **Sign-up order:** auth user → `profile_private` (birth date; a trigger rejects anyone under 16; no update policy, so it can't be changed from the app) → `profiles` (its id references `profile_private`, so there's no profile without a birth date) → `profile_instruments`, `profile_links`, `audio_clips` (files in the private `clips` storage bucket at `<user id>/<file>`, played via signed URLs).
- **Age groups:** 16–17 year olds and adults never see each other in v1. RLS on profiles, details and clip files uses `private.same_age_group()`. `get_deck` and `record_swipe` apply it too, and `private.can_message()` re-checks it on every message, so a teen pair stops chatting if one turns 18. Bands (v2) are where teens and adults will meet.
- **Location:** `profiles.lat/lng` are rounded to 2 decimals (~1 km) by trigger and can't be read or written by clients (column grants). Set them with `set_my_location()`; distances come back from `get_deck` as whole km.
- **Public API (RPC):** only `get_deck(max_km, instrument_ids, min_skill, genre_filter, goal_filter, frequency_filter, max_results)`, `record_swipe(target, decision)` (returns the match id on a mutual Jam, else null), `undo_swipe(target)` (deletes your swipe unless it made a match), `set_my_location(lat, lng)`, `has_my_location()`, and the band functions `create_band(name)`, `propose_band_member(band, candidate)`, `vote_band_member(proposal, approve)`, `answer_band_invite(proposal, accept)`, `cancel_band_proposal(proposal)`, `leave_band(band)`, `my_band_chats()`, `update_band(...)`, `set_band_clip(...)`, `get_band_deck(max_results)` and `record_band_swipe(band, decision)` (see Bands below), plus the temporary tester function `reset_my_swipes()`. Helpers live in the unexposed `private` schema; signed-in users can execute only the ones RLS policies call.
- **Tables clients write directly:** profile tables (own rows), `band_roles` (own rows), `match_reads` (own rows), `band_messages` (insert in own band, if `can_band_message`), `band_reads` (own rows in own bands), `messages` (insert in own match, if `can_message`), `blocks` (own), `reports` (insert only; read them in the dashboard). Swipes and matches are written only by `record_swipe`; either person can delete (unmatch) a match.
- **Realtime:** `matches`, `messages` and `match_reads` are in the `supabase_realtime` publication. RLS applies to inserts and updates, but Realtime sends every delete (with only the row id) to all subscribers, so an unmatch makes everyone's app reload its matches. That's fine at this size.
- **Read marks:** `match_reads` (match_id, user_id, last_read_at). Both people in a match can read both marks (for "Seen"); you can only insert or update your own, in your own matches. A trigger sets `last_read_at` to the server's `now()`. Unread counts are computed in the app from the latest 500 messages. `matches.created_by` (default `auth.uid()`, set inside record_swipe's request) records whose swipe completed the match.
- **Avatars:** the `supabase/functions/generate-avatar` Edge Function (Deno, deployed with verify_jwt) checks the caller, allows 5 per person per rolling 24 hours (`avatar_generations`, which clients can't access), and builds a riso-poster prompt from the main instrument and sanitised genres. The prompt always asks for a faceless, stylised figure, so it's never a fake photo of a person. It calls Cloudflare Workers AI `@cf/black-forest-labs/flux-1-schnell` (body is only `prompt` and `steps` 4: the model rejects any other field, even `seed`; response `result.image` is a base64 JPEG), uploads to the private `avatars` bucket at `<uid>/<millis>.jpg` with the service role, sets `profiles.avatar_path` (clients can read but not write it) and deletes the previous file. It needs the Edge Function secrets `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_API_TOKEN`; without them it answers 503 "isn't set up yet". Cost: about 58 neurons per 1024×1024 image, so the free 10,000 neurons/day cover about 170 avatars. Avatar files are readable by the same age group (policy like clips); `get_deck` returns `avatar_path`. Redeploy after editing the function (MCP `deploy_edge_function`).
- **Band roles:** `band_roles` (profile_id, instrument_id, slots 1–4, sort_order; own rows only by RLS; a trigger allows at most 8 slots in total). No rows = the default five minus your main instrument, as in the app. `get_deck` puts people whose main instrument (`private.main_instrument`) fills an open role (`private.open_band_roles`: needs minus non-blocked matches by main instrument) first, then sorts by distance. These are ordering only; nobody is hidden.
- **Card's song:** `profiles.featured_clip_id` (nullable, FK to audio_clips with on delete set null; a trigger allows only your own clips; clients can read and update this one column). `get_deck` orders a musician's `clips` with the featured one first, and cards play `clips[0]`; `loadMyCard` does the same. Set it with `ClipRepository.setFeatured` from the star on each clip in the profile's Audio clips section (tap again to clear; then the first clip plays).
- **Test data:** `supabase/seed/test_musicians.sql` adds the 8 sample musicians as adult profiles with no password (emails `@test.octava.invalid`, fixed ids ending `a1`–`a8`). Nika, Luka, Tamar and Dato have already chosen Jam on every real adult profile that existed when the script ran. `supabase/seed/remove_test_musicians.sql` deletes them and everything linked to them. They were removed on 2026-10-12 and added again on 2026-10-13. To remove them, delete their clip files through the Storage API first (Supabase blocks SQL deletes on `storage.objects`), then their auth users, which cascades to everything else. Their clips come from `supabase/seed/test_riffs.py`, which synthesises a 6-second WAV riff per musician and uploads it by signing in as each one; that needs a temporary password on the accounts (`update auth.users set encrypted_password = extensions.crypt('<temp>', extensions.gen_salt('bf')) where email like '%@test.octava.invalid'`). Since 2026-10-13 the owner has kept that password so they can sign in as a test musician; never write it into the repo. Clear it with `encrypted_password = ''`. Accounts inserted by SQL need the auth.users token columns (`confirmation_token`, `recovery_token`, `email_change*`, `phone_change*`, `reauthentication_token`) set to `''`, not NULL, or signing in fails with "Database error querying schema".
- **Bands (v2, migrations `20261013071220_bands` and `20261013071241_bands_avatars`; app: see Code layout → Bands):** `bands` (name 1–60, created_by), `band_members` (band, profile, instrument_id = their main instrument when they joined), `band_proposals` (band, candidate, proposed_by, status `voting` → `invited` → `joined` / `declined`, or `refused` / `cancelled`; one open proposal per person per band), `band_votes` (proposal, voter, approve), `band_messages`, `band_reads` (stamped by the server clock like `match_reads`). Clients write only messages and read marks; everything else goes through the functions: `create_band` makes you the first member; `propose_band_member` needs a match between you and the candidate, counts your own yes, and in a band of one sends the invite at once; `vote_band_member` refuses on any no and turns the proposal into an invite when every current member has said yes (`private.settle_proposal`); `answer_band_invite` re-checks the rules on accept; `my_band_chats()` (migration `20261013080141_band_chat_status`) returns each of your bands with whether its chat is open. `cancel_band_proposal` (migration `20261013074746_band_cancel_proposal`) lets the proposer withdraw a request while voting or invited, or any member if the proposer has left; the invite simply disappears for the candidate. `leave_band` deletes the band when the last member leaves and re-settles open votes. Limits: 12 members per band, 10 bands per person. The age rule (`private.band_age_ok`): the first person of another age group can only join a band that already has 2+ members, and `private.band_chat_open` only allows posting with 2+ members, or 3+ when teens and adults mix. Blocks between the candidate and any member stop proposals and joins (`private.blocked_in_band`). Visibility: a band, its members and messages are visible to members (`private.is_band_member`, security definer so band policies don't recurse); the invited person also sees the band and its members, but never the vote or a refusal (`private.can_see_band`). `private.knows_via_band` lets bandmates, invitees and people being voted on see each other's `profiles`, `profile_instruments` and avatar files across age groups, never their clips or links and never in `get_deck`. Storage policies can't be altered by migrations here ("must be owner of table objects"), so the avatar rule is a separate added policy. All band tables are in the Realtime publication.
- **Band cards (step 5a, migration `20261015110035_band_cards`; app: band profile in 5b, feed cards in 5c, see Code layout):** band profile columns on `bands`: `description` (≤ 500), `genres` (from the list, lower-cased, ≤ 10), `open_roles` (instrument ids, order kept, ≤ 8), `clip_path` / `clip_seconds` (the band's own clip in the private `band-clips` bucket at `<band id>/<file>`; anyone signed in can listen, members upload and delete). `private.check_band_profile` (trigger) cleans and checks them. Members edit with `update_band(band, name, description, genres, open_roles)` (null = unchanged, '' clears the description) and `set_band_clip(band, path, seconds)` (null clears; deleting the old file is up to the app). `get_band_deck(max_results)` returns band cards for you: bands you're not in, haven't swiped on (`band_swipes`) or asked to join, and could join now (`private.can_join_band`: 1–11 members, you in < 10 bands, no blocks, the age rule), with members as instrument ids only (no names or ids), `fits_you` (your main instrument is an open role; those come first). Bands with no open roles are shown too (owner's choice). `record_band_swipe(band, decision)`: a Jam inserts a join request, `band_proposals.requested = true` with no proposer; every member must approve (`vote_band_member`), then `private.settle_proposal` adds the person straight away (re-checking `can_join_band`; otherwise `refused`). The requester never sees the vote. `reset_my_swipes` also clears `band_swipes`.
- **Requests, the requester's side (migration `20261016073829_band_requests_for_requester`):** `my_band_requests()` returns your pending requests (proposal id, band id and name, when you asked; never the votes) and `withdraw_band_request(proposal)` cancels one while it's voting (only yours).
- **Removing members (owner, 2026-10-16; migration `20261016063934_band_removals`):** `band_removals` (band, target, proposed_by, status `voting` / `removed` / `refused` / `cancelled`; one open vote per person) and `band_removal_votes`. `propose_band_removal(band, target)` (not yourself: use Leave band; your yes counts), `vote_band_removal(removal, approve)`, `cancel_band_removal(removal)` (the proposer, or anyone if they left). `private.settle_removal` removes the person once **a majority of the other members** say yes (`others / 2 + 1`: 1 of 1, 2 of 2, 2 of 3, 3 of 4), refuses once that can't be reached, cancels if the target already left, and re-settles open join votes after a removal. The target can't vote on or see their removal (policies hide it). `leave_band` also re-settles removal votes. Both tables are in the Realtime publication.
- **Band message reports (migration `20261015083338_report_band_message`):** `reports.band_message_id` (on delete set null) and `reported_text` (a copy, kept if the message goes). The "File a report" policy only accepts them when the message was sent by the reported person, in a band you're in, with exactly that text.
- **Auth email:** the project uses Supabase's built-in mailer, which sends only about 2 emails an hour for the whole project; beyond that sign-up fails with `over_email_send_rate_limit` (shown as `errEmailBusy`, "Sign-ups are busy right now"). So "Confirm email" is turned off for the tester preview (since 2026-10-12): sign-up signs people straight in. Before the store launch, connect a custom SMTP sender (Authentication → SMTP, e.g. Brevo or Resend), raise Authentication → Rate Limits, and turn Confirm email back on.
- **Rule tests:** `supabase/tests/rules_check.sql` acts as fake users in one block and always ends with an exception, so it rolls itself back. Deck checks count only its own fake users, so the result doesn't depend on what else is in the database. All checks should read PASS. Re-run it after any schema or policy change, and also run the Supabase security and performance advisors.
